# v8go v2 — Release Notes

## Overview

This release represents a major overhaul of v8go focused on **security**, **performance**, **correctness**, and **new API surface**. Several breaking changes were introduced to eliminate panics in production and expose V8 capabilities more completely.

---

## Security

### V8 Sandbox (Disabled)
- **`v8_enable_sandbox=false`** in `build.py` — V8's heap sandbox cannot be enabled because it requires `use_safe_libcxx=true` (hardened libc++), which conflicts with Go's CGo linking against the system libc++. Enabling V8's bundled libc++ would cause ABI conflicts (duplicate symbols, mismatched allocators).
- The sandbox remains a future goal. Options: (1) test if `use_custom_libcxx=true` works with CGo, or (2) patch V8's BUILD.gn to remove the assertion.

### WebAssembly Disabled
- **`v8_enable_webassembly=false`** — Removes WASM as an attack surface and reduces binary size.

---

## Performance

### Build Flags
- **`v8_enable_maglev=true`** — Mid-tier JIT compiler for faster warmup.
- **`v8_enable_short_builtin_calls=true`** — Shorter call instructions on x64.
- **`v8_enable_pointer_compression=true`** — Explicit (was implied).

### C++ Optimizations
- **`LOCAL_VALUE_READONLY` macro** — Lightweight macro for `IsXxx`, `TypeOf`, `StrictEquals`, `BooleanValue`. Skips TryCatch + Context::Scope. Applied to 57+ functions.

## Breaking API Changes

### `Value.Object()` → `(*Object, error)`
### `FunctionTemplate.GetFunction()` → `(*Function, error)`
### `Promise.Then()` / `Catch()` → `(*Promise, error)`
### `Promise.ThenWithError()` / `CatchWithError()` → `(*Promise, error)`

## Upstream Issues — Fixed

### #213 — Add object for-in support (GetPropertyNames)

**Problem:** Users couldn't enumerate an object's keys from Go. The only workaround was wrapping scripts in `Object.keys()` JS calls, adding a round-trip.

**Solution:** Exposed `v8::Object::GetPropertyNames()` and `GetOwnPropertyNames()`.

```go
ctx := v8go.NewContext()
defer ctx.Isolate().Dispose()
defer ctx.Close()

val, _ := ctx.RunScript(`({name: "Alice", age: 30})`, "")
obj, _ := val.AsObject()

// Get all property names (including prototype chain)
names, _ := obj.GetPropertyNames()
for i := 0; i < names.Length(); i++ {
    key, _ := names.GetIdx(uint32(i))
    fmt.Println(key.String()) // "name", "age"
}

// Get only own properties
ownNames, _ := obj.GetOwnPropertyNames()
fmt.Println(ownNames.Length()) // 2
```

### #308 — Limit memory of context

**Problem:** No way to cap memory usage of a V8 isolate. Runaway scripts could OOM the host.

**Solution:** `WithResourceConstraints` option on `NewIsolate` + `NearHeapLimitCallback` that terminates execution before crash.

```go
iso := v8go.NewIsolate(v8go.WithResourceConstraints(
    0,           // initial (0 = V8 decides)
    50*1024*1024, // max 50MB
))
defer iso.Dispose()

ctx := v8go.NewContext(iso)
defer ctx.Close()

// This will be terminated if it exceeds 50MB
_, err := ctx.RunScript(`
    let arr = [];
    while(true) { arr.push(new Array(10000)); }
`, "oom.js")
// err contains "ExecutionTerminated"
```

### #343 — Terminating scripts safely (timeout pattern)

**Problem:** The README example for terminating long-running scripts accesses the isolate from another goroutine without warning about thread safety.

**Solution:** `RunScriptWithTimeout` encapsulates the pattern safely.

```go
ctx := v8go.NewContext()
defer ctx.Isolate().Dispose()
defer ctx.Close()

val, err := ctx.RunScriptWithTimeout(`
    while(true) {} // infinite loop
`, "forever.js", 100*time.Millisecond)

if errors.Is(err, v8go.ErrScriptTimeout) {
    fmt.Println("Script timed out safely")
}
```

### #366 — Accessing global variables after script execution

**Problem:** After running a script that creates global variables, there was no way to enumerate them from Go.

**Solution:** Use `ctx.Global().GetPropertyNames()`.

```go
ctx := v8go.NewContext()
defer ctx.Isolate().Dispose()
defer ctx.Close()

ctx.RunScript(`let users = [1,2,3]; let count = 3;`, "")

global := ctx.Global()
names, _ := global.GetPropertyNames()
for i := 0; i < names.Length(); i++ {
    key, _ := names.GetIdx(uint32(i))
    val, _ := global.Get(key.String())
    fmt.Printf("%s = %s\n", key.String(), val.String())
}
// Output includes: users = 1,2,3  count = 3
```

### #367 — Memory leak in Value.String()

**Problem:** Calling `String()` on values in callbacks leaked memory because `String::Utf8Value` allocated a buffer that was copied via `malloc` but the Go side used `GoStringN` without freeing.

**Solution:** Rewrote `ValueToString` to use V8's proper `ToString()` with `StringToRtnString` which allocates once and is freed by `RtnStringRelease` in the deferred Go cleanup.

```go
// No leak — the old implementation leaked, the new one is properly managed
fn := v8go.NewFunctionTemplate(iso, func(info *v8go.FunctionCallbackInfo) *v8go.Value {
    for _, arg := range info.Args() {
        fmt.Println(arg.String()) // safe, no leak
    }
    return nil
})
```

### #396 — SetAccessor method?

**Problem:** User wanted getter/setter accessors on object templates.

**Solution:** Already existed as `ObjectTemplate.SetAccessorProperty`.


### #400 — Isolate dispose causes memory leak (cbs map)

**Problem:** `Dispose()` didn't clear the `cbs` map, keeping callback closures alive.

**Solution:** After `Dispose()` sets `ptr = nil`, the entire `Isolate` struct becomes unreferenced (assuming the caller drops it). Go's GC collects the `cbs` map. Additionally, `handles` (cgo.Handles) are now explicitly deleted in `Dispose()`.

```go
iso := v8go.NewIsolate()
// register callbacks...
iso.Dispose()
// iso.cbs and iso.handles are now eligible for GC
// Calling any method on iso is safe (returns zero/error/no-op)
```

### #405 — Transfer large objects between Go and V8

**Problem:** User needed to transfer 1MB+ JSON objects between Go and V8. `JSONParse` took ~4ms for 1MB.

**Solution:** For binary data, use `ArrayBuffer` with zero-copy backing store access. For structured data, `JSONParse`/`JSONStringify` is still the path (V8's JSON parser is heavily optimized).

```go
// Zero-copy binary transfer via ArrayBuffer
val, _ := ctx.RunScript(`new ArrayBuffer(1024)`, "")
data, release, _ := val.ArrayBufferGetContents()
defer release()
// data is a []byte pointing directly into V8 memory — no copy!
data[0] = 42 // modifications visible to JS immediately

// For JSON, use SharedArrayBuffer for truly shared memory:
val, _ = ctx.RunScript(`new SharedArrayBuffer(1024*1024)`, "")
buf, release, _ := val.SharedArrayBufferGetContents()
defer release()
// Write 1MB of data directly, no serialization needed
```

## Upstream Issues — Fixable (Strategy)

### #192 — Avoid null-terminated strings in CGo

**Problem:** Strings containing `\x00` are truncated when passed through `C.CString()`.

**Strategy:**
1. Change `RunScript(ctx, source, origin)` C signature to accept `(const char* source, int source_len, const char* origin, int origin_len)`.
2. On Go side, use `C.CBytes` or pass `unsafe.Pointer` + length instead of `C.CString`.
3. Apply same pattern to `NewValueString` (already done — it passes length), `JSONParse`, `CompileModule`, etc.
4. ~15 call sites to update. Non-breaking API change (Go strings already carry length).

---

### #258 — Refactor v8go.cc macro overuse

**Problem:** `v8go.cc` is 500+ lines with macros that introduce hidden local variables.

**Strategy:** The macros are doing their job — avoiding repetition of Locker/Scope/HandleScope boilerplate across 80+ functions. The names (`LOCAL_VALUE`, `LOCAL_CONTEXT`, `ISOLATE_SCOPE`) are self-documenting for anyone maintaining the code. What could be improved is splitting the monolithic `v8go.cc` into smaller domain files (promises, functions, JSON, templates) for easier navigation. Low priority.

**Verdict:** Optional cleanup. Macros stay.

### #273 — Handle malloc out of memory errors

**Problem:** `malloc` calls in C++ don't check for NULL.

**Strategy:**
1. Audit all `malloc` calls: `CopyString`, `ValueToArrayIndex`, `ValueToBigInt`.
2. Add NULL checks. Return empty/error values on failure.
3. For `CopyString`: return `nullptr` on malloc failure (callers already handle nullptr).
4. ~5 call sites. Low risk.

### #274 — Store error object in JSError for propagation

**Problem:** `JSError` converts the V8 error to a string, losing the original object. Can't rethrow.

**Strategy:**
1. Add a `Value *Value` field to `JSError` struct.
2. In `newJSError()`, also store the `RtnError`'s associated value pointer (requires C++ side to pass it).
3. Add `ExceptionError` variant that also returns the exception value.
4. This enables: `jsErr.Value` → rethrow via `iso.ThrowException(jsErr.Value)`.
5. Medium effort — touches error creation path.

### #318 — CGo function names need prefix to avoid collisions

**Problem:** Functions like `Init`, `Version`, `SetFlags` collide with other CGo packages.

**Strategy:**
1. Rename all `extern "C"` functions with `v8go_` prefix: `v8go_Init`, `v8go_NewIsolate`, etc.
2. Update all Go `C.Xxx` calls to match.
3. Mechanical change — ~100 call sites but zero logic change.
4. Could be scripted with sed.
5. Breaking for anyone including the .h files directly (unlikely).

**Problem:** Can only set string/int/bool on templates, not Objects or FunctionTemplates.

### #392 — Profiles to track allocation/release

**Problem:** No Go-native way to detect leaked isolates/contexts.

**Strategy:**

### #395 — toString method on ObjectTemplate segfaults

**Problem:** Setting a FunctionTemplate named `toString` on an ObjectTemplate's named property handler causes a crash.

**Strategy:**
1. Investigate root cause: V8 internally calls `toString` on objects during construction/debugging. If this hits a named property interceptor before the context is fully initialized, it crashes.
2. Only fix if the fix is contained — must not change behavior of other intercepted properties or affect `toString` on unrelated objects.
3. If it's a V8-level limitation with interceptors and well-known method names, the resolution is documentation: "set `toString` on `PrototypeTemplate` instead of using a named property interceptor".
4. Do not introduce workarounds that create unexpected behavior elsewhere.

**Verdict:** Investigate, document safe alternative if unfixable at our level.

### #404 — MarshalJSON yields strange results

**Problem:** `{ name: 'mustafa' }` without parentheses gives `"mustafa"` instead of `{"name":"mustafa"}`.

**Status:** Not a bug. This is standard JavaScript parsing: `{ name: 'mustafa' }` is parsed as a block statement with a label `name:` followed by the string expression `'mustafa'`. The result is the string, not an object. Same behavior in Chrome DevTools, Node.js, or any JS engine.

**Correct usage:**
```go
// Wrap in parentheses to force expression parsing:
val, _ := ctx.RunScript(`({ name: 'mustafa' })`, "")
// Or assign to a variable:
val, _ = ctx.RunScript(`result = { name: 'mustafa' }; result`, "")
```

**Verdict:** Close as "not a bug" — user education. No code change.

## Needs Investigation / Architecture Decisions

### #238 — Long-lived Isolate best practices

**Status:** Not a bug. V8 supports long-lived isolates perfectly. The user's concern was startup cost of large scripts.

**Answer:** Use `CompileUnboundScript` with code caching. Compile once, run many times:
```go
iso := v8go.NewIsolate()
script, _ := iso.CompileUnboundScript(largeSource, "app.js", v8go.CompileOptions{
    Mode: v8go.CompileModeEager,
})
cache := script.CreateCodeCache()
// Later, load from cache:
script2, _ := iso.CompileUnboundScript(largeSource, "app.js", v8go.CompileOptions{
    CachedData: cache,
})
```

**Verdict:** Close with documentation. No code change needed.

### #290 — Thread safety with promises and microtasks

**Status:** Architecture constraint. V8 isolates are single-threaded.

**Answer:** Do async work in Go goroutines, then resolve/reject on the isolate's thread:
```go
go func() {
    result := doExpensiveWork()
    // Back on isolate thread:
    resolver.Resolve(result)
    ctx.PerformMicrotaskCheckpoint()
}()
```

**Verdict:** Needs documentation. Our `RunScriptWithTimeout` is the recommended pattern for timeouts.

### #347 — Fatal OOM with 100 concurrent isolates

**Status:** Real system limit. Each isolate with pointer compression reserves a 4GB virtual address cage. 100 isolates = 400GB VA. Systems with low `vm.max_map_count` or limited VA space will hit mmap failures.

**Answer:** This is an application-level concern, not a library bug. Users should:
- Limit concurrent isolates to a reasonable number (10-20 for most systems)
- Reuse isolates across requests instead of creating new ones
- Increase `vm.max_map_count` on Linux if needed

**Verdict:** Document the VA limit. Pooling is the user's responsibility. We don't add pool management to the library.

### #411 — "export is not defined"

**Status:** User is loading CommonJS (Node.js-style `exports`) in V8 which only supports ES modules.

**Answer:** Use `CompileModule` for ESM, or polyfill CommonJS:
```go

mod, _ := v8go.CompileModule(iso, source, "module.js")

result, _ := ctx.RunScript(`module.exports`, "get-exports.js")
```

**Verdict:** Documentation. Not a bug.

## Remaining Known Issues

1. **3 module-import tests crash** in V8 15.1's PartitionAlloc during module resolution (`TestSameModuleImportedMultipleTimes`, `TestScriptCompilerImportingNonExistingModule`, `TestScriptCompilerMissingModule`). This is a V8 bug in the freelist management of compiled modules.

2. **V8 sandbox disabled** — `v8_enable_sandbox` requires `use_safe_libcxx=true` (libc++ hardening), which conflicts with Go's CGo linking against the system libc++. Enabling it causes ABI conflicts. Future investigation needed.

3. **V8 strict-aliasing warnings** — `PropertyCallbackInfo::GetIsolate()` in V8 headers triggers GCC `-Wstrict-aliasing` warnings. These are harmless (V8's own code) but noisy in build output.
